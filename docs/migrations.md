# Database Migrations

The analytics database schema is managed with [Alembic](https://alembic.sqlalchemy.org). This repository has no `make migrate-*` targets from the shared [migrations guide](https://github.com/softwareone-platform/mpt-extension-skills/blob/main/knowledge/migrations.md): schema migrations are Alembic revisions, and there are no data migrations.

Changes that affect users of the server between versions are described in [version-migrations.md](version-migrations.md).

## Layout

- [`alembic.ini`](../alembic.ini) and [`alembic/env.py`](../alembic/env.py): Alembic configuration
- [`alembic/versions/`](../alembic/versions): revision scripts
- [`mpt_mcp/analytics/models.py`](../mpt_mcp/analytics/models.py): SQLAlchemy table definition (`mcp_events`), the source for autogenerated revisions

`alembic/env.py` reads `ANALYTICS_DATABASE_URL` and converts the `postgresql+asyncpg://` URL to a synchronous `postgresql://` URL for Alembic.

## When Migrations Run

The HTTP server applies `alembic upgrade head` on startup when `ANALYTICS_DATABASE_URL` is set (`run_migrations()` in [`runtime/migrations.py`](../mpt_mcp/runtime/migrations.py)). A failed migration is logged and the server keeps running without a working analytics database. The server passes `configure_logger=False`, so Alembic does not replace the server's logging configuration.

## Creating A Migration

1. Change the table in [`mpt_mcp/analytics/models.py`](../mpt_mcp/analytics/models.py).
2. Start the local database with `make run-analytics` (or `docker compose --profile analytics up -d analytics-db`).
3. Generate the revision from a shell in the app container (`make bash`):

```bash
export ANALYTICS_DATABASE_URL=postgresql+asyncpg://mcp_user:mcp_password@analytics-db:5432/mcp_analytics
alembic revision --autogenerate -m "add column x"
```

4. Review the generated file in `alembic/versions/`: keep both `upgrade()` and `downgrade()`, and keep the generated revision message as it is.
5. Apply it with `alembic upgrade head` or by restarting the server.

Migrations must stay backward compatible with the running server version, because a new revision is applied by the first instance that starts with it.
