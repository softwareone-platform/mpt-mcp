# Version Migrations

This document lists the changes between versions that require action from users of the server or from developers of this repository. Analytics database migrations are described in [migrations.md](migrations.md).

Add an entry to the `Unreleased` section in the same change that introduces a breaking change.

## Unreleased

- The servers start from the `mpt_mcp.runtime` package: the HTTP server runs with `python -m mpt_mcp.runtime.runner` instead of `python -m mpt_mcp.server`, and the stdio server with `python -m mpt_mcp.runtime.stdio` instead of `python -m mpt_mcp.server_stdio`. Update local MCP client configurations that run the stdio server; the Docker image, `compose.yaml`, the `make` targets and [`examples/`](../examples/README.md) already use the new modules. uvicorn loads the app from `mpt_mcp.runtime.main:app`.
- The package is renamed from `src` to `mpt_mcp`. Local MCP client configurations that ran `python -m src.server_stdio` must run `python -m mpt_mcp.runtime.stdio` (see the previous entry).
- The HTTP and stdio servers serve the same tools and resources. The stdio server gains the documentation tools and the `api://openapi.json` and `docs://` resources, and validates `MARKETPLACE_API_TOKEN` before its first query. The debug tools `marketplace_cache_info`, `marketplace_refresh_cache` and `marketplace_resources_info` are only available when `DEBUG=true` in both servers, so the HTTP server no longer lists `marketplace_resources_info` in production.
- `marketplace_query` no longer accepts `page`: the Marketplace API only paginates with `limit` and `offset`, and it rejected the `page` parameter with 400 Bad Request. Use `offset` instead (`offset = (page - 1) * limit`).
- The stdio server loads the OpenAPI spec of `MARKETPLACE_API_BASE_URL` (`{endpoint}/public/v1/openapi.json`), as the HTTP server does for its caller's endpoint. `OPENAPI_SPEC_URL` is no longer read: remove it from `.env` files and MCP client configurations.
- Tool failures are MCP tool errors (`isError: true`) instead of successful results with an `{"error": ...}` payload. The text is the error message, followed by its hints (`hint`, `did_you_mean`, `example`…) as JSON. `marketplace_docs_read` no longer returns `count: 0` for a missing page and `marketplace_refresh_cache` no longer returns `success: false`: both fail instead. Clients that read `error` from the result must check `isError`.
- `marketplace_resources` returns only the `resource` and `summary` of each resource unless a `category` is given, and no longer returns `example_queries` or `get_full_schema`. The full catalog, with the descriptions and generated examples of every resource, took 137,000 characters on production and 211,000 on `api.s1.show` when this changed, more than MCP clients such as Claude Code accept in one tool result, so they saved it to a file instead of showing it to the model. The compact list took about 35,000 characters on both. The new `category` argument returns the `path`, `description`, `filterable_fields` and `enum_fields` of one category's resources, and `search` filters by name or summary. `example_queries` and `get_full_schema` only repeated the resource name in a fixed call; use `marketplace_resource_info` for real examples and `marketplace_resource_schema` for the fields.
- `marketplace_query` on `catalog.products` without `select` returns only `id`, `status`, `name` and `shortDescription` (`select=-*,+id,+name,+shortDescription`, plus `status`, which is always kept). It used to send `+id,+name,+shortDescription`, which the API reads as fields to add to the default ones, so every product field came back. A page of products then filled the model's context with fields it rarely needs and, with many items, went over what MCP clients accept in one tool result. Pass a `select` to get other fields.
- The `marketplace_quick_queries` tool is removed, with its 17 templates. They were fixed text with placeholder IDs, and some were wrong: "Expiring soon" filtered subscriptions by `endDate`, which they do not have, and the buyer statuses listed `Inactive`, which does not exist. The common questions are now MCP prompts with arguments (`recent_orders`, `orders_by_status`, `orders_for_product`, `search_products`, `products_by_vendor`, `agreements_for_client`, `subscriptions_for_product`, `subscriptions_due`, `search_buyers`); the other templates were plain status or order filters, which `marketplace_resource_info` and the RQL operators in the server instructions cover. Analytics records prompt use as `prompt_get` events, with the prompt name in `tool_name`.
- The `api://openapi.json` and `docs://` resources fail with an MCP error when they cannot be read, instead of returning the error as their content: `api://openapi.json` returned a JSON object with `error`, `message` and `hint`, and `docs://` returned the error message as the page text. Clients that read those fields from the content must handle the error of the resource read.
- `SSE_DEFAULT_BASE_URL` is renamed to `HTTP_DEFAULT_BASE_URL`, and `SSE_DEFAULT_BASE_URL` is no longer read: rename it in `.env` files and deployments.
- The `SSE_ENABLED`, `SSE_HOST`, `SSE_PORT`, `SSE_CORS_ORIGINS`, `TOOL_INCLUDE_PATTERNS` and `TOOL_EXCLUDE_PATTERNS` environment variables are no longer read. They had no effect and can be removed from `.env` files.
- `marketplace_query` rejects a `limit` over 100 or below 0, and a negative `offset`, with an MCP validation error before calling the API. A `limit` over 100 used to be cut to 100 without notice, and a negative `offset` was sent to the API. The input schema now publishes the range (`minimum: 0`, `maximum: 100`, `default: 10`), so clients can see it before calling. Pass `limit` up to 100 and page on with `offset`.
- When the OpenAPI spec of the caller's endpoint cannot be loaded, `marketplace_resources`, `marketplace_resource_info`, `marketplace_resource_schema` and `marketplace_audit_fields` fail with the same error as `marketplace_query`: `Failed to load OpenAPI spec for your endpoint`, with `api_endpoint`, `details` and `hint`. They used to fail with `Failed to load OpenAPI spec` and only `details` (`marketplace_audit_fields`: `... for audit fields`, with `api_endpoint`).
- `marketplace_resource_info` and `marketplace_resource_schema` fail on an unknown resource with the same error as `marketplace_query`: `Unknown resource: '<name>'`, with `hint`, `available_categories` and `did_you_mean`. `marketplace_resource_info` used to return only `hint`, and neither suggested similar resources. `available_categories` is now sorted in the three tools.
- `marketplace_resource_schema` returns `common_queries` as `marketplace_query` calls built from the resource's item fields, such as `marketplace_query(resource='commerce.orders', rql='eq(type,Purchase)', limit=10)`, instead of query strings such as `commerce.orders?eq(status,Active)&limit=20`. The old strings were the same for every resource, used `status`, `name` and `id` even when the resource has no such field, and gave single-item resources a `limit`. `with_filters`, `with_sorting`, `with_select` and `full_example` are only given when the item fields allow them, and single-item resources get only `basic` and `with_select`.
- For developers of this repository: `mpt_mcp/tools/resources.py` is now the `mpt_mcp/tools/resources/` package (`tool.py`, `listing.py`, `info.py`, `schema.py`), and its `execute_marketplace_*` functions are replaced by `list_resources`, `describe_resource_info` and `describe_resource_schema`, which return the response models. The OpenAPI lookups are methods of `OpenAPISpec` (`mpt_mcp.marketplace.schemas`): `resolve_ref`, `resolve_schema` and `get_item_schema`, which were functions of `mpt_mcp.marketplace.audit_fields`, and `get_operation`, `get_response_schema` and `get_response_item_schema`. `MarketplaceSpec` moved to `mpt_mcp.tools.spec` and holds an `OpenAPISpec` in `openapi` instead of the spec dict in `openapi_spec`; its `get_endpoint` replaces `get_endpoint_path` of `mpt_mcp.tools.query.paths`, and `get_item_fields` replaces `get_allowed_select_fields` of `mpt_mcp.tools.query.params`.
- For developers of this repository: the tools are registered on a FastMCP `LocalProvider` per module (`query_tools` in `mpt_mcp.tools.query`, `resource_tools` in `mpt_mcp.tools.resources`, `debug_tools` in `mpt_mcp.tools.debug`), which `create_mcp_server()` adds with `mcp.add_provider()`. The OpenAPI resource, the prompts and the documentation tools and resource are registered the same way (`openapi_resources` in `mpt_mcp.resources`, `marketplace_prompts` in `mpt_mcp.prompts`, `documentation_provider` in `mpt_mcp.documentation.server`, which replaces the mounted documentation server). `register_query_tools`, `register_resource_tools`, `register_debug_tools`, `register_resources`, `register_prompts` and `create_documentation_server` are removed, the `api://openapi.json` resource function is `read_openapi_spec`, and `mpt_mcp/tools/query.py` is now the `mpt_mcp/tools/query/` package. The tools get the API client and the endpoint spec as `Depends(get_api_client)` and `Depends(get_marketplace_spec)` from `mpt_mcp.tools.dependencies`, and the spec loading functions raise `OpenAPISpecFetchError` for every failure.
